Vorion — BASIS & CogniGate

~8ms p50 / ~20ms p95 policy decisions (same-region)

Agentic AI systems tend to fail in a specific way: an agent takes an action — calls a tool, moves money, deletes a record — with no enforced boundary on what it's allowed to do, and no reliable record of why it was allowed. Vorion is a vendor-neutral answer to that. BASIS is an open specification defining an eight-rung trust ladder, T0 through T7, from "no established trust" to "fully autonomous within its scope." CogniGate is the policy-enforcement engine that reads that ladder: every agent tool-call is checked against the tier it's cleared for before it executes, and the decision — allow, needs-approval, or block — is written to an auditable, replayable record. CogniGate is Apache-2.0 and open source.

Three products sit around that core. AgentAnchor is a public trust registry — an agent's tier and attestation history are checkable, the way certificate-transparency logs work for TLS. Aurais is a security console for people running fleets of agents: anomaly detection against a learned baseline, one-click chain inspection, and quarantine-on-click when something looks wrong. Rainbow is the analytics layer over all of it — fleet-wide tier distribution, trust-score velocity, and drift detection.

I submitted an RFI response to NIST's AI Risk Management Framework based on this work, and filed a provisional patent (March 2026) for a model-identity fingerprinting method used to detect when a model has been silently swapped or has drifted from its known baseline.

BanquetAI

1,000+ tests in the stewarding module alone

Event and banquet operations run on paperwork nobody enjoys: a Banquet Event Order (BEO) gets typed up, an equipment list gets built from it by hand, and someone in the back of house turns that into an actual pull sheet — trays, linens, chafers — usually under time pressure, usually more than once a day. BanquetAI automates that chain: it extracts and categorizes BEO line items automatically, a drag-and-drop schematic builder calculates equipment requirements from the room layout, and a stewarding engine turns all of it into a requisition with ratio calculations and pull sheets already generated.

Built on Firebase and Next.js, with 1,000+ tests in the stewarding module alone and 75%+ overall coverage — and it went out to real venue operators, not just a demo.

The most useful thing that came out of building it wasn't the product itself — it was watching what happens when you put an AI "employee" in the loop of a real operation and ask it to be right, not just fast. The trust and accuracy questions that came up doing that are what turned into Vorion.

agent-memory-service

100% current-fact accuracy · 0% stale · ~35% token savings

Most agent-memory systems get scored with one number, and that number hides two different failure modes. The first is retrieval: can the system find the right facts at all. The second is currency: when a fact changes mid-conversation — you say you live in Denver, then later say Lisbon — does the system answer with what's true now, or what used to be true? A flat vector store retrieves both the old and new fact, since they're semantically similar, with no notion that one of them is dead: measured directly, a naive store answers changing-fact questions correctly 0% of the time and surfaces the stale value in its top 5 every single time.

agent-memory-service is a typed four-store memory layer — working, episodic, semantic, procedural — built around the fix: supersession. When a new value for a fact arrives, the old one is marked inactive and drops out of the active retrieval set, the same bi-temporal idea Graphiti and Zep use. A 4-configuration ablation (flat → +recency → +consolidation → +supersession) isolates each piece's real contribution, evaluated on a controlled synthetic set and on LoCoMo-10, the field-standard long-conversation benchmark. The full system reaches 100% current-fact accuracy with 0% stale retrieval, and consolidating raw turns into deduplicated facts cuts grounding-context token cost by about a third. Every number reproduces from a clean clone — no API key required for the retrieval numbers.

genealogy-graphrag

relational recall@5 0.000 → 1.000 · MRR@10 0.77 → 1.00

There's a class of question dense embeddings and keyword search structurally cannot answer: "who is the maternal grandfather of X," where the answer's name never appears anywhere near the question in the source text. No amount of better embeddings fixes that — the relationship has to be resolved, not searched for. genealogy-graphrag pairs a standard hybrid retriever (BM25 + dense, cross-encoder reranked) with a typed kinship-graph resolver that walks the actual family graph to answer relational questions directly. On the relational subset, recall@5 goes from 0.000 with retrieval alone to 1.000 with graph resolution; overall MRR@10 rises from 0.77 to 1.00 once reranking is layered on top.

It runs on a dual graph backend behind one interface — in-memory NetworkX for a zero-setup evaluation, Neo4j/Cypher for real hop-bounded traversal in production — and every answer carries a bibliographic citation, not just a confidence score.

cason-heritage

66 individuals · 12 generations · 7 evidence tiers

This site is the stress test for the same architecture as agent-memory-service, run on the messiest data there is: four centuries of real, contradictory, incomplete genealogical records. The problem shape is identical to production AI memory — sources conflict, multiple candidates compete for the same generational slot, and one wrong claim silently corrupts every record downstream that inherits from it.

Every individual on the direct line carries one of seven evidence tiers, from confirmed-by-primary-source down through possible, unlikely, and disproven-claim — nobody enters the confirmed line without a primary source. Disproven records aren't deleted, they're quarantined with their disqualification reasoning intact, so a future researcher can't accidentally resurrect a myth that's already been ruled out. Behind the narrative is a small governed agent system — the "Living Line" — a roster of research agents that read the family knowledge graph, propose findings on the open questions, and gate every claim through an auditable policy before it reaches the record. The rule the whole thing runs on: propose, never publish.

governed-agents

full NDJSON audit trail

A smaller, standalone demonstration of the same governance idea behind Vorion: wrap every LLM tool-call in a named-rule policy gate, so nothing executes without first being checked against a rule set — a name, a threshold, an enforcement level — and every decision gets written out as a TraceEvent in NDJSON, one JSON record per line, so the whole run replays and audits cleanly.

It runs multi-model consensus across Claude, Gemini, and Grok rather than trusting a single model's judgment, and has a "Red Cell" adversarial mode built specifically to try to find gaps in the policy coverage rather than confirm it works.
