// 01 · the through-line

Operations first, for twenty-five years.

The instinct that eventually built AI infrastructure was trained on ballrooms, not codebases.

1999 → 2024 · catering, then hotels

Luxury and volume are a seesaw

Catering since 1999, hotels and resorts since 2006 — luxury properties, high-volume convention venues, theme parks. The through-line is systems thinking under pressure: luxury and volume sit on opposite ends of the same board, and the only way to serve both is to build the counterweights and the ramps before the room fills. You do not get to debug a banquet at 6pm. Everything that can be decided in advance has to be decided in advance, and everything that can't has to have a documented fallback.

2025 · banquetai

The operations problem became a software problem

BanquetAI started as the thing I wanted to exist: a Banquet Event Order goes in, a categorized equipment layout and a stewarding pull sheet come out. It went to market with real venue operators. It also surfaced the question that changed the work — when an AI system hands an operator a number, what exactly is that number standing on?

2026 · vorion

Trust needed to be infrastructure, not a disclaimer

The agent-trust and accuracy problems that surfaced building BanquetAI led directly to Vorion: a vendor-neutral runtime-governance layer for agentic AI, built around an open trust-tier specification and a policy-enforcement engine that checks every agent action against it before it runs. Same instinct as the ballroom — decide what's allowed while there's still time to decide, and leave an auditable record of who decided it.

now

Same architecture, applied to my own family

This site is the proof-of-work. Four centuries of contradictory genealogical records run through the same provenance grading as the agent systems, governed by a roster of research agents that propose but never publish. If the architecture can't survive being pointed at my own ancestors, it has no business being pointed at anyone's production traffic.

// 02 · how I work

Rules I actually enforce.

Not aspirations — each of these is wired into something on this site, and each was learned by getting it wrong first.

rule 01

Green CI is not a security signal

A passing pipeline tells you the tests you wrote still pass. It tells you nothing about the resolved dependency tree underneath. The tree is the signal; the checkmark is a mood.

Learned auditing an 80+ repository estate for dependency vulnerabilities.
rule 02

Read the source table before you quote the number

A latency figure on this site was once wrong twice: the first version cited the fastest endpoint in a table instead of the relevant one, and the correction cited the right endpoint in the wrong system. The honest fix was to publish a design target and label it a target. Two mis-attributions in a row on a number I cared about is exactly why the rule exists.

Documented in this repo's claims manifest, in full, including the wrong version.
rule 03

Agents propose. They never publish.

The research agents on this site open pull requests against the record; a human merges them. An agent that can write directly to the thing it's researching isn't a researcher, it's an unreviewed author with a schedule.

The governed agent roster behind The Cason Line.
rule 04

A self-claim is worth zero trust

"We're compliant" is not evidence. An assertion only counts once something independent can check it — a signed attestation, a reproducible run, a build provenance record. Design for the checker, not the claim.

The premise of the whole BASIS trust-tier spec.
rule 05

Every number reproduces from a clean clone

If a metric on my résumé can't be regenerated by someone who just cloned the repo and ran the harness, it isn't a metric — it's marketing. This is why the evaluation work ships with the ablation, not just the result.

Standing rule across every open-source project listed on the portfolio.
rule 06

Govern the public record like production

An automated auditor checks what this site says about me — every metric, every status, every claim — against its source on a schedule, because a résumé is just a database that nobody put constraints on. Including this page. Including the book count below.

The Public Record Auditor, run weekly against the claims manifest.
